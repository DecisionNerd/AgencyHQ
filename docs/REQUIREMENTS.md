# Baseline requirements

IDs are stable. R-005 was restated and R-020 added on 2026-09-07 (ADR-0006).
R-003, R-012, and R-013 were clarified and R-021–R-025 added for the accepted
Compose/container target on 2026-09-08 (ADR-0008). Target requirements do not
claim current implementation; qualification evidence is pending where marked.

| ID | Requirement | Acceptance evidence |
| --- | --- | --- |
| R-001 | The coordinator shall be the only component that commits scope, dispatch, and acceptance transitions; the Lead proposes within delegated authority and the coordinator validates and records. | Domain policy and authority tests. `reject` command (`apps/coordinator/src/commands/reject.ts`) and `invalidate_acceptance` command (`apps/coordinator/src/commands/invalidate-acceptance.ts`) both require the coordinator to find a ledger record before writing any transition. |
| R-002 | Postgres shall persist the decision, actor, causation, generation, and DispatchIntent before any task is triggered. | Transaction and replay tests. |
| R-003 | Every worker attempt shall run as its own Trigger run in an isolated attempt checkout/worktree at the contract's base revision, under the contract's permission rules, without usable upstream push credentials. The target deployed profile uses one disposable task container per run. | Adapter tests; execution trial.  Pending: deployed-container qualification C4–C7. |
| R-004 | Trigger.dev shall be the execution runtime, trusted for run lifecycle, duration limits, status, and cancellation, and never for acceptance; each runtime profile shall declare which boundaries it enforces. | Classification tests; execution trial. |
| R-005 | AgencyHQ shall implement no coding-agent loop and no model-provider adapters; all model calls, including the Lead's, go through OpenCode. | Dependency review. |
| R-006 | Acceptance shall require approved criteria met by exact outputs, passing `verify.run` results, the required Review, a recorded acceptance Decision, and any `humanRequired` Approval bound to the same versions. For a `merge` boundary the `approve` command follows the same post-acceptance path as `onAcceptFinal`. | Acceptance tests including false-success cases; `flow.parking (a)` (null-commit → contract failure, no artifact); `flow.parking (b)` (humanRequired → `pending_human`, replay no-op); `approve.test.ts` (approve matching version → completed including merge-boundary cases v–vii; mismatch → `APPROVAL_VERSION_MISMATCH`); execution trial item 8 (Slice 4, 2026-09-08). |
| R-007 | The system shall classify execution, contract, and process failures separately; only execution failures create automatic new Attempts, within budget. | Table tests over Trigger final statuses. |
| R-008 | Dispatch shall follow explicit rank, preserve the main effort's identity when blocked, serialize attempts per repository, and record every exception. | Allocation tests; `packages/domain/test/dispatch.campaign.test.ts` (Slice 5, 2026-09-08): campaign-aware ordering — main effort first, remaining members by rank/createdAt/id, items without campaignId unaffected; no new skip reason introduced. |
| R-009 | Any widening of scope, capability, boundary, budget, or review depth shall be a new StepContract version validated against delegated authority; workers cannot request it. | Authority subset tests; `packages/domain/test/authority.update.test.ts` (Slice 5, 2026-09-08): `proposeAuthorityUpdate` requires strictly increasing version (integer-major comparison of leading digit) and valid schema; `apps/coordinator/test/integration/control-plane-rework.test.ts` (`T-13: invalidate_acceptance leaves step_contracts row unchanged` — control-plane integration test verifies `step_contracts.id`, `status`, and `criteria_digest` are unchanged after `invalidate_acceptance`). |
| R-010 | Dispatch, observation, token issuance, integration, and operator commands shall be idempotent by the identities in EXECUTION_MODEL.md; every task observation shall be recorded. | Duplicate-delivery tests; `apps/coordinator/test/integration/flow.observations.test.ts`. |
| R-011 | The web app shall show contract, execution, verification, and acceptance states distinctly with source and timestamp, using Trigger Realtime for execution state. | Browser tests (Slice 5, 2026-09-08): `apps/web/e2e/work-item.spec.ts` — five state cards (pending-human-accept, completed, admitted, blocked with finding, merge-boundary with integration card); `apps/web/e2e/return-view.spec.ts` — return view renders Changed/Decisions/Stops/Continuing sections. |
| R-012 | The default deployment shall be a Compose-managed AgencyHQ application, separate AgencyHQ Postgres, self-hosted Trigger webapp and deployed worker stack, and persistent OpenCode setup/authentication, started from the repository root with one Compose command. No host agent process is required; additional services need a concrete requirement and ADR. | Pending: ADR-0008; clean-start, restart, and real execution qualification. Existing host deployment is a fallback. |
| R-013 | Stopping an attempt shall revoke its generation before cancellation, retain available checkpoints and stop evidence beyond execution teardown, and display *stopping* until trusted termination or effective isolation is confirmed and Trigger reports a final status. Abrupt loss of unexported changes shall be explicit; timeout alone never proves termination. | Execution trial items 2 and 4 (Slice 4, 2026-09-08); `apps/coordinator/test/integration/flow.stop.test.ts`; persistence tests.  Pending: durable container stop/worker-loss qualification C7. |
| R-014 | The Lead shall approve criteria and profile before dispatch; workers report results and cannot alter criteria, checks, or acceptance. Weakened or removed tests are not protected verifier-configuration paths and are not caught by tamper detection; they are detected only by the adversarial reviewer (`lead.review`). | Adapter and domain tests; `flow.false-success (f): weakened test — review blocks, no verifier_tampered, work item not completed` (`REVIEW_BLOCKING`); `flow.integrity.test.ts` (three tests: agree, omit, union case — coordinator unions adapter and own set, records both sides in evidence); `verify-run-core.test.ts` (H-6: `protectedPathsSource`); trial. Observation (three live runs, Slice 4 trial, 2026-09-08): the adversarial reviewer reads verification stderr and refuses a criterion whose check is a placeholder. |
| R-015 | WorkItem completion shall cover the declared boundary with exact revisions; integration shall be compare-and-set and serialized per repository. | `apps/coordinator/test/integration/flow.integrate.test.ts`; `trigger/test/integrate-merge-core.test.ts`; execution trial items 8 (merge boundary + human approval), 9 (CAS base_moved), 10 (two-repo manifest — Slice 4, 2026-09-08). |
| R-016 | Dispatch shall reject a contract requiring a boundary the active runtime profile declares advisory; nested agents are denied until descendant accounting exists. `deploy` boundary is not yet implemented (`DEPLOY_NOT_SUPPORTED`). | Domain tests; `packages/domain/src/authority/runtime.ts`. |
| R-017 | Findings shall receive an owned disposition without widening the contract. | Disposition tests; `apps/coordinator/test/integration/flow.remediate.test.ts`. `invalidate_acceptance` (Slice 5, 2026-09-08): inserts new `invalidate` decision; historical accept decision and step contract rows are never modified. |
| R-018 | Contract repair shall supersede, never rebind; evidence and Reviews do not transfer across versions. | Version tests; `apps/coordinator/test/integration/flow.manifest.test.ts`; `apps/coordinator/test/integration/flow.manifest-next.test.ts`. |
| R-019 | A returning operator shall see changes, pending decisions, continuing runs, observation freshness, and requested-vs-confirmed stop status without logs. | Browser tests (Slice 5, 2026-09-08): `apps/web/e2e/return-view.spec.ts` (4 tests); `apps/web/e2e/approve.spec.ts` (2 tests); `apps/web/e2e/reject.spec.ts` (3 tests); `apps/web/e2e/stop.spec.ts` (2 tests — (vi-a) asserts attempt id and `contract v\d+` on the running seeded item (wiBlocked) and proves "stopping" state; (vi-b) asserts `contract v\d+` from the open pending decision on wiApprove; full stop cycle covered by integration tests). Unit test: `apps/web/test/control-plane-helpers.test.ts` ("pause confirm message names version when there is no open decision") covers the pause-without-open-decision path. Live trial item: approve via operator UI on real stack — see [trials/2026-09-slice5.md](engineering/trials/2026-09-slice5.md). |
| R-020 | Repository content and Lead proposals shall be untrusted input; a proposal can only narrow delegated authority, never widen it. | Adversarial-fixture authority tests. |
| R-021 | A fresh checkout shall start all required services, apply migrations, generate internal credentials, and register the execution image through `docker compose up -d`; retries and restarts shall preserve data and valid credentials without duplicate bootstrap resources. | Pending: Compose first-start/restart/failure-recovery trial. |
| R-022 | Operators shall configure providers through OpenCode's login flow in the setup container; authorized task containers shall reuse persisted authentication after recreation, with verified refresh/logout behavior and no secrets in logs or images. | Pending: provider authentication and recreation/concurrency trial for each claimed login flow. |
| R-023 | Every execution stage shall materialize exact source/artifact revisions independently of host paths or a previous container; attempt/checkpoint objects, manifests, and stop evidence shall remain inspectable after container deletion, with generation-validated admission. | Pending: cross-container artifact, cancellation, stale-generation, and integrity tests. |
| R-024 | Eligible runs shall execute concurrently in separate task containers from the same registered image while preserving rank, repository serialization, slot/provider/budget limits, and safe replacement; adding capacity shall not require login in every task container. | Pending: two-project parallel execution, same-repository serialization, capacity and worker-loss trial; second-host proof before multi-machine claims. |
| R-025 | The web interface shall show actionable service/provider/worker readiness and support linking a repository, setting authority, and starting work without SQL or test seeds; provider auth and source-control access shall remain distinct. | Pending: fresh-install operator journey and first real bounded repair. |

Unit, Postgres integration, and dependency-rule tests exist; see
